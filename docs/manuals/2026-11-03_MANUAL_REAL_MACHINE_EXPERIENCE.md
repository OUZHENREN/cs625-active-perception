## 1. RVS 报「TCP 等待连接时间超时」

```text
症状：RVS 界面红字「TCP 等待连接时间超时」；我们这侧触发后完全没应答
真因：RVS_AI_Center 没连上（不是相机问题、不是网络问题、不是端口问题）
处置：以【管理员方式】重新启动 RVS_AI_Center
确认：tasklist.exe | grep -i "RVS_AI_Center"  应能看到进程；端口 2024 OPEN
预防：每次开始视觉作业前先确认 RVS_AI_Center 在跑
```

**为什么它会导致"没有位姿"**：RVS 的粗匹配需要 AI 提供 2D 种子，AI 掉线 → 粗匹配无输入 →
直接返回 `NG,POSE,0,0,0,0,0`。

## 2. 客户端 `no answer after N s`（RVS 其实回了）

```text
症状：rvs_pose_client 打印 "no answer after 45s"，但 RVS 窗口没报错
真因：RVS 回了 'NG,POSE,0,0,0,0,0'（位姿未找到），
     师兄的 tcp_server 只解析 S*/R* 开头的报文，
     日志里只有一行 WARN "Unknown msg type: 'NG'"，然后什么也不发布。
确认：看 tcp_server 的输出里有没有 'NG,POSE'
     （这也是为什么客户端超时先怀疑 RVS_AI，而不是网络）
处置：先解决第 1 条（RVS_AI），或改善取景（见第 10 条）
```

## 3. 规划一律 99999 失败

```text
症状：plan_joint_locked 返回 plan code 99999 / points 0；
     换 IK 种子、给已验证关节角都没用
真因：手动拖动把腕关节绕成累积角，超出 URDF 限位 ±360°
     例：wrist_1 = −424.9°、wrist_3 = +462.8°
     MoveIt 的关节空间被限位约束，起始状态在范围外 → 规划器直接失败
确认：读出关节角，与限位比对（肘 ±180，其余 ±360）
处置：在示教器/自由拖动下把超限关节拨回 ±180 内
     技巧：跨过 ±360 时读数会自动归零，所以只需拨"剩余那几十度"，不是拨一整圈
预防：① 尽量用程序移动，少用手拖；
     ② 手拖之后先读关节角，确认都在 ±180 内再开始作业
```

## 4. 保护停止后臂不动（状态话题却全绿）

```text
症状：控制器接受了目标，臂一动没动，执行器报 NO_MOTION；
     safety_mode=1、robot_mode=7、arm_controller=active 全都正常
真因：反控通道（50001/50003/50004）被机器人侧关闭
     （保护停止会终止机器人上的 external_control 脚本）
确认：ss -tn | grep -E ":5000[134] " 应有 3 条 ESTAB
处置：bash scripts/recover_control.sh          # 轻量：只重发脚本 + 恢复速度滑条
     （不要用完整版，见第 5 条）
预防：执行器已内置"NO_MOTION 且端口不在 → 自动重发并返回码 10"；
     但保护停止后 60 s 内禁止自动重发（见第 7 条）
```

## 5. 恢复后臂下沉 / 位置漂移

```text
症状：执行 recover 之后 TCP 突然低了十几毫米（实测 0.5605 → 0.5441）
真因：完整恢复脚本会 deactivate + activate 控制器，伺服瞬间释放，
     负载下臂会自由下坠一点
处置：默认只用 scripts/recover_control.sh（轻量，不动控制器）；
     scripts/recover_control_full.sh 仅在轻量恢复无效时使用，
     且空载或有人扶稳时才允许
预防：携带工件时绝不调用完整恢复
```

## 6. 力矩值突变到 0

```text
症状：静止时 Σ|effort| ≈ 0.46（承载 6.8 kg 工件时绝不可能）
真因：控制器切换（deactivate/activate）后 effort 状态接口丢失数据
处置：重启驱动栈（SIGINT 停 launch 进程组 → 重新 launch → 激活控制器）
确认：静止时 Σ|effort| 应 ≈ 15.8（空载+工具），远大于 0
预防：执行器已内置 EFFORT_DEAD 门：力矩峰值 <1 时拒绝运动（exit 11）
```

## 7. 保护停止后"恢复—重试"导致连续碰撞

```text
症状：一次碰撞后连续 2–3 次撞在同一处，越撞越重
真因：保护停止 = 物理事件（撞到了东西）+ 反控掉线；
     自动重发 + 自动重试等于"闭着眼再撞一次"
处置（已固化为规则）：
     ① 保护停止后 60 s 内禁止自动重发重试（执行器已实现，写 /tmp 标记）
     ② 序列层遇到 exit 9/11 一律终止，不重试
     ③ 人工先看现场：撞到的是什么？为什么？
预防：接近高风险区域（夹具/插槽）前必过 13b 位姿门 + 包络门
```

## 8. 手动微动后抓取姿态歪掉

```text
症状：手拖/微动过关节后，去抓工件时夹爪歪着，蹭到工件把手
真因：手动动过关节但没人复验 TCP —— 曾出现位置只差 4.3 mm、姿态差 12.09°
处置：进抓取区前必须过 5b/6b 位姿门（1.5 mm / 0.10°）
     用 scripts/teaching/adjust_tcp.py 迭代收敛
预防：任何手动动作之后，进抓取区前重跑位姿门；这是 5b 存在的理由
```

## 9. `--time-scale` 语义搞反

```text
症状：以为"半速"，实际跑成两倍速，直接撞桌子
真因：--time-scale 是【乘】在轨迹时间戳上：
     >1 → 时间变长 → 更慢；  <1 → 时间变短 → 更快
处置：需要一半速度就传 2.0，不是 0.5；<1.0 已被脚本拒绝
```

## 10. 观测位"必须偏很远"才拍得到

```text
症状：固定粗观测位怎么调都拍不到工件，手拖偏 300 mm 才行
真因：该位姿是【平视取景】（光轴只向下 9.3°），工件压在画面下边缘
     （占垂直半视场 73%），可用区域只有几厘米
处置：用 scripts/teaching/view_geometry_check.py 量化：
     俯角、工件投影像素、画面余量（mm）、安全行程
     选俯角 25–45°、安全行程 > 80 mm 的位姿
预防：登记粗观测基准前先跑自检，判 NARROW/FLAT 的一律不用
```

## 11. 夹爪电流读到天文数字

```text
症状：gripper.py status 返回 current_a = −1.4e15 / 2.6e10
真因：夹爪桥的电流回传坏
处置：抓持判定只看 position_mm（≥40 mm 表示张紧夹住）；
     gripper.py 已把不可信电流替换为 null 并标注
```

## 12. MoveIt 刷 `Missing gripper_right_finger_joint`

```text
症状：move_group 每次循环都警告状态不完整
真因：描述里实例化了夹爪宏，带两个真机永不发布的手指关节
     （夹爪由 Windows 桥控制，不走 ros2_control）
处置：夹爪宏改为【仅仿真】实例化（2026-11-03 已改）
确认：真机描述展开后非固定关节应为 6 个
```

## 13. ROS 相机与 RVS 抢相机

```text
症状：一边能出图，另一边收不到点云 / 报设备忙
真因：相机同一时刻只能被一个进程占用
处置：用 RVS 前先停 percipio 相机驱动（SIGINT 到 launch 进程组，不要 pkill）
     用 ROS 相机前先关 RVS 的图像采集
```

## 14. 工件朝向与 RVS 识别率（所有者实测，2026-11-03）

**坐标系约定**：以机械臂基座坐标系 X 轴为基准，逆时针为正。

```text
已确认可用区间：
  A 类（工件【扶手面/大面】朝向机械臂）：−45° ~ 0° 可用，实测识别率约 0.9
  · 其余角度【尚未探索】，不要当成已知结论使用

实际使用频率：目前 −45° ~ +45° 这一段用得最多
```

**因此要开发两套基准**：

```text
基准 A（现有）：面向 −45° ~ 0° 的工件朝向，已可用
基准 B（待开发）：面向 +45° 的工件朝向
  设计原则：工件逆时针多转了多少，机械臂观测方位就跟着转多少，
            让扶手面重新正对相机（不是靠算法容忍斜视）
  期望：+45° 工况下识别率回到 A 类的 0.9 水平
```

**已验证（2026-11-03 21:07）**：

```text
基准 A（所有者手摆的当前位姿）：T2 识别成功
基准 B：T2 三帧一致 3.0 mm / 0.52°，识别成功
  TCP (0.7288, 0.0239, 0.6588)
  quat (−0.1025, 0.9348, 0.3370, 0.0462)
  关节 [−8.9, −90.1, −83.9, −101.9, 134.7, 171.6]
  方位角 88.2°，俯角 45°，距瞄准点 (0.790, 0.683, 0.20) 约 1.05 m

两套基准已登记在 config/tasks/common.yaml 的 teaching_observation_baselines
```

**采集纪律（同轮新增）**：测量识别率时工件必须【静止】。所有者转动工件期间采集的三帧
对应三个不同摆放，这种记录是"测量无效"，不能计入失败率——本轮就出现过一次这样的误判。

**2026-11-03 21:20 补充结论（所有者实测）**：

```text
工件在 −60° 以内、几乎任意位置都能被识别；但【靠近 0° 放置时识别率大大下降】
（注意：是显著下降，不是绝对不能识别）。
→ 识别率不是"离基准位多近"的函数，而是"工件呈现给相机的是哪个面/哪个角度"的函数。
→ 因此基准位不能按"角度等分"设计，必须按实测识别窗口划界（详见
  docs/worklogs/2026-11-03_WORKLOG_OBSERVATION_BASELINES_AND_ACCURACY.md）。
```

**踩坑记录（重要）**：曾试图把 J6 从 +171.6° 改到 −8.4°（两者相差 180°）。
实测这两支解对应同一相机位置，但 −8.4° 那支在本机模型里**自碰撞**
（tool0↔forearm_link、forearm_link↔wrist_2_link），且因腕部非球形，
翻转后法兰位置还偏了 256 mm。**J6 大体量不是可自由选择的，它由相机位姿决定。**
若一定要小 J6，只能移动相机点（roll 180 那支 J6=+4.5°，但相机要偏 0.29 m）。
## 通用开工检查清单（每次上真机前）

```text
1. 四项门：safety=1、robot=7、arm_controller active、
   control_health.py 的 sockets/controller/joint_states 全 True
2. 反控三端口：ss -tn | grep -E ":5000[134] " → 3 条 ESTAB
3. 力矩活着：静止 Σ|effort| ≈ 15.8（不是 0）
4. 关节都在 ±180° 内（手拖过之后尤其要查）
5. 夹爪状态：position_mm 合理（0 = 闭合空载，≥40 = 张紧夹持）
6. RVS 侧：RVS_AI_Center 在跑（管理员方式），界面无「TCP 等待连接超时」
7. 相机归属：RVS 与 ROS 相机驱动不能同时占用
```
