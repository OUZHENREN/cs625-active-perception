## 1. RVS 报「TCP 等待连接时间超时」

```text
症状：RVS 界面红字「TCP 等待连接时间超时」；我们这侧触发后完全没应答
真因：RVS_AI_Center 没连上（不是相机问题、不是网络问题、不是端口问题）
处置：以【管理员方式】重新启动 RVS_AI_Center
确认：tasklist.exe | grep -i "RVS_AI_Center"  应能看到进程；端口 2024 OPEN
预防：每次开始视觉作业前先确认 RVS_AI_Center 在跑
```

**为什么它会导致"没有位姿"**：RVS 的粗匹配需要 AI 提供 2D 种子，AI 掉线 → 粗匹配无输入 →
直接返回 `NG,POSE,0,0,0,0,0`。

## 2. 客户端 `no answer after N s`（RVS 其实回了）

```text
症状：rvs_pose_client 打印 "no answer after 45s"，但 RVS 窗口没报错
真因：RVS 回了 'NG,POSE,0,0,0,0,0'（位姿未找到），
     师兄的 tcp_server 只解析 S*/R* 开头的报文，
     日志里只有一行 WARN "Unknown msg type: 'NG'"，然后什么也不发布。
确认：看 tcp_server 的输出里有没有 'NG,POSE'
     （这也是为什么客户端超时先怀疑 RVS_AI，而不是网络）
处置：先解决第 1 条（RVS_AI），或改善取景（见第 10 条）
```

## 3. 规划一律 99999 失败

```text
症状：plan_joint_locked 返回 plan code 99999 / points 0；
     换 IK 种子、给已验证关节角都没用
真因：手动拖动把腕关节绕成累积角，超出 URDF 限位 ±360°
     例：wrist_1 = −424.9°、wrist_3 = +462.8°
     MoveIt 的关节空间被限位约束，起始状态在范围外 → 规划器直接失败
确认：读出关节角，与限位比对（肘 ±180，其余 ±360）
处置：在示教器/自由拖动下把超限关节拨回 ±180 内
     技巧：跨过 ±360 时读数会自动归零，所以只需拨"剩余那几十度"，不是拨一整圈
预防：① 尽量用程序移动，少用手拖；
     ② 手拖之后先读关节角，确认都在 ±180 内再开始作业
```

## 4. 保护停止后臂不动（状态话题却全绿）

```text
症状：控制器接受了目标，臂一动没动，执行器报 NO_MOTION；
     safety_mode=1、robot_mode=7、arm_controller=active 全都正常
真因：反控通道（50001/50003/50004）被机器人侧关闭
     （保护停止会终止机器人上的 external_control 脚本）
确认：ss -tn | grep -E ":5000[134] " 应有 3 条 ESTAB
处置：bash scripts/recover_control.sh          # 轻量：只重发脚本 + 恢复速度滑条
     （不要用完整版，见第 5 条）
预防：执行器已内置"NO_MOTION 且端口不在 → 自动重发并返回码 10"；
     但保护停止后 60 s 内禁止自动重发（见第 7 条）
```

## 5. 恢复后臂下沉 / 位置漂移

```text
症状：执行 recover 之后 TCP 突然低了十几毫米（实测 0.5605 → 0.5441）
真因：完整恢复脚本会 deactivate + activate 控制器，伺服瞬间释放，
     负载下臂会自由下坠一点
处置：默认只用 scripts/recover_control.sh（轻量，不动控制器）；
     scripts/recover_control_full.sh 仅在轻量恢复无效时使用，
     且空载或有人扶稳时才允许
预防：携带工件时绝不调用完整恢复
```

## 6. 力矩值突变到 0

```text
症状：静止时 Σ|effort| ≈ 0.46（承载 6.8 kg 工件时绝不可能）
真因：控制器切换（deactivate/activate）后 effort 状态接口丢失数据
处置：重启驱动栈（SIGINT 停 launch 进程组 → 重新 launch → 激活控制器）
确认：静止时 Σ|effort| 应 ≈ 15.8（空载+工具），远大于 0
预防：执行器已内置 EFFORT_DEAD 门：力矩峰值 <1 时拒绝运动（exit 11）
```

## 7. 保护停止后"恢复—重试"导致连续碰撞

```text
症状：一次碰撞后连续 2–3 次撞在同一处，越撞越重
真因：保护停止 = 物理事件（撞到了东西）+ 反控掉线；
     自动重发 + 自动重试等于"闭着眼再撞一次"
处置（已固化为规则）：
     ① 保护停止后 60 s 内禁止自动重发重试（执行器已实现，写 /tmp 标记）
     ② 序列层遇到 exit 9/11 一律终止，不重试
     ③ 人工先看现场：撞到的是什么？为什么？
预防：接近高风险区域（夹具/插槽）前必过 13b 位姿门 + 包络门
```

## 9. `--time-scale` 语义搞反

```text
症状：以为"半速"，实际跑成两倍速，直接撞桌子
真因：--time-scale 是【乘】在轨迹时间戳上：
     >1 → 时间变长 → 更慢；  <1 → 时间变短 → 更快
处置：需要一半速度就传 2.0，不是 0.5；<1.0 已被脚本拒绝
```

## 10. 观测位"必须偏很远"才拍得到

```text
症状：固定粗观测位怎么调都拍不到工件，手拖偏 300 mm 才行
真因：该位姿是【平视取景】（光轴只向下 9.3°），工件压在画面下边缘
     （占垂直半视场 73%），可用区域只有几厘米
处置：用 scripts/teaching/view_geometry_check.py 量化：
     俯角、工件投影像素、画面余量（mm）、安全行程
     选俯角 25–45°、安全行程 > 80 mm 的位姿
预防：登记粗观测基准前先跑自检，判 NARROW/FLAT 的一律不用
```

## 14. 工件朝向与 RVS 识别率（所有者实测，2026-11-03）

**坐标系约定**：以机械臂基座坐标系 X 轴为基准，逆时针为正。

```text
已确认可用区间：
  A 类（工件【扶手面/大面】朝向机械臂）：−45° ~ 0° 可用，实测识别率约 0.9
  · 其余角度【尚未探索】，不要当成已知结论使用

实际使用频率：目前 −45° ~ +45° 这一段用得最多
```

**因此要开发两套基准**：

```text
基准 A（现有）：面向 −45° ~ 0° 的工件朝向，已可用
基准 B（待开发）：面向 +45° 的工件朝向
  设计原则：工件逆时针多转了多少，机械臂观测方位就跟着转多少，
            让扶手面重新正对相机（不是靠算法容忍斜视）
  期望：+45° 工况下识别率回到 A 类的 0.9 水平
```

**采集纪律（同轮新增）**：测量识别率时工件必须【静止】。所有者转动工件期间采集的三帧
对应三个不同摆放，这种记录是"测量无效"，不能计入失败率——本轮就出现过一次这样的误判。

**2026-11-03 21:20 补充结论（所有者实测）**：

```text
工件在 −60° 以内、几乎任意位置都能被识别；但【靠近 0° 放置时识别率大大下降】
（注意：是显著下降，不是绝对不能识别）。
→ 识别率不是"离基准位多近"的函数，而是"工件呈现给相机的是哪个面/哪个角度"的函数。
→ 因此基准位不能按"角度等分"设计，必须按实测识别窗口划界（详见
  docs/worklogs/2026-11/2026-11-03_WORKLOG_OBSERVATION_BASELINES_AND_ACCURACY.md）。
```

**踩坑记录（重要）**：曾试图把 J6 从 +171.6° 改到 −8.4°（两者相差 180°）。
实测这两支解对应同一相机位置，但 −8.4° 那支在本机模型里**自碰撞**
（tool0↔forearm_link、forearm_link↔wrist_2_link），且因腕部非球形，
翻转后法兰位置还偏了 256 mm。**J6 大体量不是可自由选择的，它由相机位姿决定。**
若一定要小 J6，只能移动相机点（roll 180 那支 J6=+4.5°，但相机要偏 0.29 m）。
## 15. 角度数据的 ± 到底指什么

```text
坐标系：base_link（X 向前、Z 向上，REP-103）
符号：绕 +Z 轴，右手定则 → 俯视逆时针为正 → +X 转向 +Y
所有"工件偏了多少度""相机方位角"都按这个口径读写，不要混用别的约定
```

## 16. RVS 测量极不稳定，一次触发靠不住

```text
· 同一姿态连续触发，返回值可能相差几百毫米（2026-11-05 实测三帧相差 920 mm）
· 位置一变、灯光一差就 NG；A/B 两个观测基准都要多次尝试
· 结论：RVS 不是"一次测量"，而是"多次采样 + 一致性筛选"
  现在的做法：fitness ≥0.9/0.8 + 帧间一致性 + 位姿库比对，三道筛子叠加
```

## 17. 抓取段必须慢 + 必须反复核验

```text
关节跟踪容差 0.0005–0.0008 rad，在 353 mm 力臂上就是 0.5–1.0 mm 的 TCP 误差，
所以"发完指令就当到了"必然偏。
现行做法：抓取接近 0.016 m/s（末段再慢 4 倍）、下降到抓取位 0.008 m/s，
到位后用 5b/6b 门复验（1.5 mm / 0.4°），超差走 adjust_tcp.py 闭环。
```

## 18. 插入间隙只有 1–2 mm，示教器手工对齐不可能

```text
所有者实测：槽与工件前后间隙 1–2 mm，手工用示教器对齐根本做不到，
多次尝试都卡在插入中途。
所以最后几毫米必须靠：−10° 倾斜楔形导入 + 力/力矩事件判定，而不是人眼对齐。
```

## 19. 改预插入位姿必须同步改插入位姿

```text
预插入与插入是同一条链条上的两个点：
  insert = 槽位姿 × T_s_tcp
  rotated = insert × Ry(−10°)
  pre_insert = rotated 沿自身 z 后退
只改起点不改终点 → 相对几何被破坏 → 下降方向不再指向槽口 → 反复碰撞。
允许的一致性关系只有三种：整体刚性平移 / 只改高度 / 改倾斜角重新推导。
每次改完必须打印两个位姿并回算校验（误差应为 0.00 mm）。
```

## 20. 竖直沿工具轴插入的实测结论

```text
做法：预插入位沿工具 z 轴后退 350 mm + 抬升 100 mm；
     下降时每 10 mm 一步、每步从实测位姿重新锚定（避免累积漂移）。

实测（2026-11-04）：
  分段行程 90 + 90 + 118 + 54 + 10 mm

## 21. 装配公差极紧：372 mm 不是物理意义上的底部

```text
三次独立尝试都在 371–372 mm 被机器人自身力矩保护挡住（重复性 1.1 mm）：
  ① 倾斜 10° 直接下插   ② 恢复姿态后再插   ③ 退出 98 mm → 转 2° → 重插
下插过程中残差单调上升（+2.7 → +4.6 → +5.0 → +5.7），是"越挤越紧"的特征。

所有者现场确认：工件不仅碰到槽底，还同时碰到两处槽壁（三面接触）。
→ 三面接触意味着任何微小姿态误差都会被两侧壁同时夹住，
  单方向直插不可能到底；必须先"让空间"再插。
```

## 22. 无六维力时，"微抖动"不能完成插入（已暂停）

```text
抖动策略成立的前提是"知道往哪个方向让"——需要接触力的方向。
本机只有关节力矩标量 Σ|τ|：只能告诉你阻力多大，分不出 x 顶住还是 y 顶住。

而这次装配是三面接触、间隙 1–2 mm，盲搜的有效方向空间极小，
每次失败尝试都在把工件往槽壁里压 → 风险远高于收益。
所有者裁决：暂停该方向，直到具备力方向感知。
```

## 23. 该工件的装配策略（所有者口述，本项目最核心的工艺知识）

```text
① 初始插入阶段：让工件绕 TCP 的 Y 轴小幅转动，以获得较宽松的区域
   （右乘：T @ Ry(θ)，TCP 点固定、工件远端摆动，与师兄写法一致）
② 随深度增加，可转空间减小，末段仍应保留约 1.5° 的转动空间
③ 插入过程中检查 Y 轴两端间隙，正常左右各约 2 mm
④ 必须"边转边插"：直接插入会让空间越来越小、阻力越来越大，直至插不动
⑤ 要检查左右间隙是否平衡，否则最后"绕 TCP 转 10°"的阻力会大很多
⑥ 判定到底后沿 Y 左右横移（每步 1 mm，共 ±2 mm）放大间隙

代码：scripts/teaching/assembly_search.py（绕 TCP 自身 Y 轴、末段 1.5°、
      y 漂移报警、位姿门）。软件不因力矩取消，只有示教器保护能停。

## 25. 网络丢包会让机械臂"看起来像程序没启动"

```text
现象：反控端口 50001/50003/50004 一条都没有，robot_task_running=false，
     dashboard play 返回 False，resend 报 success 但端口仍不出现。
真因：机器人网口 76% 丢包（50 个 ping 只回 12 个），而相机 0% 丢包（同网段对照）。
     驱动日志刷屏 PrimaryPort ... End of file。
处置：换交换机端口 → 0% 丢包。

排障顺序（别从最上层猜）：
  ① ping -c 50 -i 0.2 <机器人IP>     丢包率是第一判据
  ② ping 相机做同网段对照           立刻区分"网络"与"对端"
  ③ 看驱动日志有无 PrimaryPort 刷屏
  ④ 以上都正常，才查"程序是否在跑"
```

## 26. 网络恢复 ≠ 连接恢复

```text
丢包从 76% 降到 0% 之后，反控端口仍是 0 ——
因为驱动与机器人的主端口连接已在丢包期间被打断，网络好了不会自动恢复。
处置：SIGINT 停 launch 进程组 → 重新 launch → 端口随即恢复 3 条。

另一种同源故障：端口 3 条、task_running=true、速度滑条 100%、硬件接口 active，
但机械臂"接受目标后 10 秒不动"（NO_MOTION）→ 同样只能重启驱动栈
（重新上传并播放 external_control 程序）。
```

## 29. 槽内"转 10°"：把"能转多少度"当成测量量

```text
现象：装入后对工件绕 TCP 转 10°（师兄流程的收尾动作）会卡死。
原因：夹爪张开 50 mm、整体插在槽内约 370 mm 深，外廓与槽壁间隙 1–2 mm；
     转 10° 会让夹爪两侧在槽内扫过约 35 mm → 必然顶壁
     （实测：满深度下转 1° 就触发保护停止）。

所有者给出的关键判据：正常座好的工件【仍有约 1.5° 的自由转动空间】。
→ 于是"能转多少度"本身就是装配是否到位的测量量，而不是必须达到 10° 的指标。

实现 scripts/teaching/straighten_in_slot.py：
  · 绕 TCP 自身 Y 轴右乘，0.5° 一步，TCP 点不动
  · 每步读 Σ|effort|，残差突增 >1.0 判为"碰到槽壁" → 回退到上一步的好姿态
  · 报告 MAX FREE ROTATION；不做任何强转
截至 2026-11-13：本动作仍**未在真机验收**（源码已确认，未跑通）。

判读：
  转不动（<0.5°）→ 装配过紧或姿态偏
  约 1.5°        → 正常座好
  能转满 10°     → 槽比预期松，需检查是否插到底
