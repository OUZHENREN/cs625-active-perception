## 1. RVS 报「TCP 等待连接时间超时」

```text
症状：RVS 界面红字「TCP 等待连接时间超时」；我们这侧触发后完全没应答
真因：RVS_AI_Center 没连上（不是相机问题、不是网络问题、不是端口问题）
处置：以【管理员方式】重新启动 RVS_AI_Center
确认：tasklist.exe | grep -i "RVS_AI_Center"  应能看到进程；端口 2024 OPEN
预防：每次开始视觉作业前先确认 RVS_AI_Center 在跑
```

**为什么它会导致"没有位姿"**：RVS 的粗匹配需要 AI 提供 2D 种子，AI 掉线 → 粗匹配无输入 →
直接返回 `NG,POSE,0,0,0,0,0`。

## 2. 客户端 `no answer after N s`（RVS 其实回了）

```text
症状：rvs_pose_client 打印 "no answer after 45s"，但 RVS 窗口没报错
真因：RVS 回了 'NG,POSE,0,0,0,0,0'（位姿未找到），
     师兄的 tcp_server 只解析 S*/R* 开头的报文，
     日志里只有一行 WARN "Unknown msg type: 'NG'"，然后什么也不发布。
确认：看 tcp_server 的输出里有没有 'NG,POSE'
     （这也是为什么客户端超时先怀疑 RVS_AI，而不是网络）
处置：先解决第 1 条（RVS_AI），或改善取景（见第 10 条）
```

## 3. 规划一律 99999 失败

```text
症状：plan_joint_locked 返回 plan code 99999 / points 0；
     换 IK 种子、给已验证关节角都没用
真因：手动拖动把腕关节绕成累积角，超出 URDF 限位 ±360°
     例：wrist_1 = −424.9°、wrist_3 = +462.8°
     MoveIt 的关节空间被限位约束，起始状态在范围外 → 规划器直接失败
确认：读出关节角，与限位比对（肘 ±180，其余 ±360）
处置：在示教器/自由拖动下把超限关节拨回 ±180 内
     技巧：跨过 ±360 时读数会自动归零，所以只需拨"剩余那几十度"，不是拨一整圈
预防：① 尽量用程序移动，少用手拖；
     ② 手拖之后先读关节角，确认都在 ±180 内再开始作业
```

## 4. 保护停止后臂不动（状态话题却全绿）

```text
症状：控制器接受了目标，臂一动没动，执行器报 NO_MOTION；
     safety_mode=1、robot_mode=7、arm_controller=active 全都正常
真因：反控通道（50001/50003/50004）被机器人侧关闭
     （保护停止会终止机器人上的 external_control 脚本）
确认：ss -tn | grep -E ":5000[134] " 应有 3 条 ESTAB
处置：bash scripts/recover_control.sh          # 轻量：只重发脚本 + 恢复速度滑条
     （不要用完整版，见第 5 条）
预防：执行器已内置"NO_MOTION 且端口不在 → 自动重发并返回码 10"；
     但保护停止后 60 s 内禁止自动重发（见第 7 条）
```

## 5. 恢复后臂下沉 / 位置漂移

```text
症状：执行 recover 之后 TCP 突然低了十几毫米（实测 0.5605 → 0.5441）
真因：完整恢复脚本会 deactivate + activate 控制器，伺服瞬间释放，
     负载下臂会自由下坠一点
处置：默认只用 scripts/recover_control.sh（轻量，不动控制器）；
     scripts/recover_control_full.sh 仅在轻量恢复无效时使用，
     且空载或有人扶稳时才允许
预防：携带工件时绝不调用完整恢复
```

## 6. 力矩值突变到 0

```text
症状：静止时 Σ|effort| ≈ 0.46（承载 6.8 kg 工件时绝不可能）
真因：控制器切换（deactivate/activate）后 effort 状态接口丢失数据
处置：重启驱动栈（SIGINT 停 launch 进程组 → 重新 launch → 激活控制器）
确认：静止时 Σ|effort| 应 ≈ 15.8（空载+工具），远大于 0
预防：执行器已内置 EFFORT_DEAD 门：力矩峰值 <1 时拒绝运动（exit 11）
```

## 7. 保护停止后"恢复—重试"导致连续碰撞

```text
症状：一次碰撞后连续 2–3 次撞在同一处，越撞越重
真因：保护停止 = 物理事件（撞到了东西）+ 反控掉线；
     自动重发 + 自动重试等于"闭着眼再撞一次"
处置（已固化为规则）：
     ① 保护停止后 60 s 内禁止自动重发重试（执行器已实现，写 /tmp 标记）
     ② 序列层遇到 exit 9/11 一律终止，不重试
     ③ 人工先看现场：撞到的是什么？为什么？
预防：接近高风险区域（夹具/插槽）前必过 13b 位姿门 + 包络门
```

## 9. `--time-scale` 语义搞反

```text
症状：以为"半速"，实际跑成两倍速，直接撞桌子
真因：--time-scale 是【乘】在轨迹时间戳上：
     >1 → 时间变长 → 更慢；  <1 → 时间变短 → 更快
处置：需要一半速度就传 2.0，不是 0.5；<1.0 已被脚本拒绝
```

## 10. 观测位"必须偏很远"才拍得到

```text
症状：固定粗观测位怎么调都拍不到工件，手拖偏 300 mm 才行
真因：该位姿是【平视取景】（光轴只向下 9.3°），工件压在画面下边缘
     （占垂直半视场 73%），可用区域只有几厘米
处置：用 scripts/teaching/view_geometry_check.py 量化：
     俯角、工件投影像素、画面余量（mm）、安全行程
     选俯角 25–45°、安全行程 > 80 mm 的位姿
预防：登记粗观测基准前先跑自检，判 NARROW/FLAT 的一律不用
```

## 14. 工件朝向与 RVS 识别率（所有者实测，2026-11-03）

**坐标系约定**：以机械臂基座坐标系 X 轴为基准，逆时针为正。

```text
已确认可用区间：
  A 类（工件【扶手面/大面】朝向机械臂）：−45° ~ 0° 可用，实测识别率约 0.9
  · 其余角度【尚未探索】，不要当成已知结论使用

实际使用频率：目前 −45° ~ +45° 这一段用得最多
```

**因此要开发两套基准**：

```text
基准 A（现有）：面向 −45° ~ 0° 的工件朝向，已可用
基准 B（待开发）：面向 +45° 的工件朝向
  设计原则：工件逆时针多转了多少，机械臂观测方位就跟着转多少，
            让扶手面重新正对相机（不是靠算法容忍斜视）
  期望：+45° 工况下识别率回到 A 类的 0.9 水平
```

**采集纪律（同轮新增）**：测量识别率时工件必须【静止】。所有者转动工件期间采集的三帧
对应三个不同摆放，这种记录是"测量无效"，不能计入失败率——本轮就出现过一次这样的误判。

**2026-11-03 21:20 补充结论（所有者实测）**：

```text
工件在 −60° 以内、几乎任意位置都能被识别；但【靠近 0° 放置时识别率大大下降】
（注意：是显著下降，不是绝对不能识别）。
→ 识别率不是"离基准位多近"的函数，而是"工件呈现给相机的是哪个面/哪个角度"的函数。
→ 因此基准位不能按"角度等分"设计，必须按实测识别窗口划界（详见
  docs/worklogs/2026-11/2026-11-03_WORKLOG_OBSERVATION_BASELINES_AND_ACCURACY.md）。
```

## 16. RVS 测量极不稳定，一次触发靠不住


## 19. 改预插入位姿必须同步改插入位姿

```text
预插入与插入是同一条链条上的两个点：
  insert = 槽位姿 × T_s_tcp
  rotated = insert × Ry(−10°)
  pre_insert = rotated 沿自身 z 后退
只改起点不改终点 → 相对几何被破坏 → 下降方向不再指向槽口 → 反复碰撞。
允许的一致性关系只有三种：整体刚性平移 / 只改高度 / 改倾斜角重新推导。
每次改完必须打印两个位姿并回算校验（误差应为 0.00 mm）。
```

## 33. 绝对不要用 `ensure_robot_ready --force` 来"同步"手动拖过的机械臂

```text
事故（2026-11-20）：
  · 所有者手动拖动机械臂后，按"先重挂再动"的做法执行了
      python3 scripts/ensure_robot_ready.py --force
  · 结果机械臂**抽搐着快速跳回**上一次轨迹的终点（TCP 从 0.670/0.497 跳到 0.672/0.255，
    y 方向 240 mm），所有者当场看到"速度比较快而且发生了抽搐"。

真因：
  · arm_controller 把**最后一条轨迹的终点**当作"保持目标"；
  · 人手拖动机械臂后，控制器的目标没有变，仍停在旧终点；
  · resend_external_script（--force 做的就是这件事）会让控制器把这个旧目标重新下发给机器人
    → 机械臂跳回旧位置。跳得小就执行（抽搐），跳得大就被机器人以速度超限拒收（示教器刷屏）。
  · 之前示教器上那 4 万多条 velocity violation 就是这个机制的另一面。

  · 手动拖过机械臂后，**不要**执行 ensure_robot_ready --force / recover_control.sh；
```

## 36. WSL 系统时钟往回跳：机械臂"卡住/摆动"与测量不稳的真正元凶

```text
症状（2026-11-20 傍晚起，越来越频繁）：
  · 轨迹执行到一半停住不动，几秒后突然加速追上；所有者描述为"到位后不停、来回摇摆"

根因：WSL 的系统时钟被反复往回拨
  · dmesg 累计 1235+ 次 "Time jumped backwards"
  · 实测 30 秒内出现 4 次倒退，**最大一次 5526 毫秒（5.5 秒）**
  · 我们的轨迹只有 6 秒长 → 执行期间必然遇到时间倒退
  · 控制器按 ROS 时间戳推进轨迹，时间倒退 → 它停在原地"等时间追上"→ 恢复后再跳

更隐蔽的连带影响：测量流程靠时间戳配对彩色帧与深度帧。
  时钟一跳，配对错乱 → 点云错位 → 覆盖率与姿态估计随机变差。
  同一相机位姿在修好时钟前后：0.887（REFUSE） → 0.972（3/3 可信）。

为什么重启 timesyncd 反而更糟：
  WSL2 里有两个时间调整者 —— Hyper-V 的 TimeSync（从 Windows 主机同步）
  和 systemd-timesyncd（从 NTP 服务器同步）。两者互相拉扯就是反复跳变的来源。

规矩（2026-11-20 所有者执行）：
  1. WSL 里**关闭** systemd-timesyncd，只留 Hyper-V 主机同步：

  2. 验证（必须满足才允许跑轨迹）：
         python3 - <<'EOF'
         import time
         prev=time.time(); worst=0
         for _ in range(300):
             time.sleep(0.1); now=time.time()
             worst=max(worst, prev-now); prev=now
         print(f"最大倒退 {worst*1000:.0f} ms")
         EOF
     判据：**0 ms**（小于 100 ms 才可接受）。
  3. 时钟不稳时不要下运动指令——所有"机械臂不听话"的现象先查这一项：
         dmesg | grep -c "Time jumped backwards"

判据速查：如果机械臂运动是"连续匀速"的，时钟正常；如果表现为"停—冲—停"，
先查时钟，不要怀疑规划和轨迹代码。
```


| 指标 | 门槛 | 说明 |
|---|---|---|
| 覆盖率中位 | **≥0.95** | 0.90–0.95 只算"可接受但证据偏弱"，**不得**登记为示教位（所有者 2026-11-20 定） |

## 43. 抓取点的权威定义：一次手工验证 + 相对变换（2026-11-24 定）

## 44. 预抓取位必须比抓取位再往外 10 mm（否则电机保护座撞工件）

```text
症状（2026-11-24 所有者指出）：从预抓取位垂直下降到抓取位时，
夹爪后方的电机保护座会先蹭到工件表面，下降根本走不完。

真因：预抓取位如果正好在抓取位的正上方，下降路径贴着工件外表面，
而工具本体从 TCP 向后延伸（vendor 碰撞网格 z ∈ [−0.360, −0.146]），
这段体积在垂直下降时会扫过工件。

规矩（所有者 2026-11-24 定）：
  预抓取位 = 抓取位 + 150 mm 垂直 + **10 mm 沿"从工件指向抓取点"的水平方向**
  即 descent 不是纯垂直，而是带 10 mm 侧向分量，给电机保护座留出间隙。

  2026-11-24 实测（最终采用 −Y 方向，因为 +Y 会撞）：
    grasp     = (0.854356, 0.616288, −0.060332)
    预抓取位  = (0.854356, 0.606288,  0.089668)   ← 沿 −Y 外移 10 mm + 垂直 150 mm
    判断依据  ：+Y 方向最近工件点仅 0.8 mm（会撞），−Y 方向 17.2 mm（安全）
    下降路径  ：带 10 mm 侧向分量，不是纯垂直

  示教模式的等价做法（pose_math.py）：grasp = nominal − R@[10 mm, 0, 0]，
  把 10 mm 退让做进抓取点；效率模式改为做进预抓取位，效果相同且更直观。
```

### 靠近工件必须减速

```text
所有者要求：示教模式对接近段做了很夸张的减速；效率模式至少要降到 50%。

执行器已有机制（不需要新代码）：
  --tail-fraction F --tail-scale S
  把轨迹最后 F 比例的**时间**拉长 S 倍 → 该段速度降为 1/S。

config 里固化（approach_slowdown）：
  tail_fraction: 0.4      # 最后 40% 行程进入减速段
  tail_scale:    2.0      # 降为 50% 速度
  descent_scale: 2.0      # 预抓取 → 抓取 的纯下降段，全程 50%

用法示例（下降段全程半速）：
  python3 scripts/execute_assembly_chunks.py <plan> --tail-fraction 1.0 --tail-scale 2.0
```

## 47. "进程还活着、ROS 图里却没有发布者"——先查 /dev/shm 僵尸段

```text
症状（2026-11-20 出现两次）：
  · move_group 进程在（ps 看得到），但 ros2 node list 里没有它，/check_state_validity 不可用
  · 相机同样：进程在、日志还在打帧率，但 /camera/camera 节点下没有任何发布者
  · 日志里反复出现：
      [RTPS_TRANSPORT_SHM Error] Failed init_port fastrtps_port7005: open_and_lock_file failed

真因：FastDDS 给每个参与者建 /dev/shm/fastrtps_<hash> 段；进程异常退出（SIGKILL、
崩溃）时段文件残留。残留段占住端口，新进程建参与者失败 → 节点"半死"。
实测当天 /dev/shm 里累积了 100 个段，最早的来自前一天。

处置：
  python3 scripts/clean_dds_shm.py            # 只报告
  python3 scripts/clean_dds_shm.py --clean    # 清理（只删没有活进程占用的）
  已接入 start_real_stack.sh：每次起栈前自动 --clean --threshold 8

**第一版清理脚本是错的**（必须记住）：
  它只扫 /proc/<pid>/maps，把 `_el`（事件循环）文件当成僵尸删了——
  但 `_el` 是 open() 打开的普通文件、**不出现在 maps 里**，结果删掉了**在用**的段，
  运行中的驱动栈通信直接断掉（joint_states 收不到、规划服务消失）。
  修复：占用检测同时扫 maps 与 fd，且 `_el` 的死活跟随它的主段。
  判据：运行中执行清理应报"在用 N，僵尸 0"。
```

## 48. 接近工件必须用笛卡尔直线，绝不能用关节空间插值（三次碰撞的真因）

```text
事故（2026-11-24，一天内三次）：
  用 plan_pose_ik + execute_assembly_chunks 做"接近/下降到工件"的动作，
  目标点都正确（推导验证过），但机械臂在半路扫到工件，两次撞动工件、一次触发急停。
  最后一次实测：目标 (0.8594, 0.5296, 0.0895)，实际停在 (0.8875, 0.5527, 0.2767)，
  偏离 38 mm / 23 mm，离工件点云只剩 **2.7 mm**。

真因（方法错误，不是参数问题）：
  plan_pose_ik + execute_assembly_chunks 走的是**关节空间直线**——
  六个关节同时线性插值。关节空间直线 ≠ 末端直线。
  离工件很近时，末端实际路径是弧线，所以"垂直下降 150 mm"会斜着扫过工件。
  而规划场景里没有工件（第 45 条），这些工具也拦不住。

规矩（2026-11-24 所有者要求，必须遵守）：
  ① **接近/下降/退出工件** → 用 scripts/move_tcp_linear.py（笛卡尔直线，步长 2–3 mm）
  ② 关节空间运动只用于**远离工件**的换位（站位之间、观测位、回停车位）
  ③ 距离工件 < 200 mm 时，禁止使用关节空间运动
  ④ move_tcp_linear 现在自带点云间隙闸：每一步规划前先算到工件点云的最近距离，
     < CLEARANCE_MIN_M(15 mm) 直接 REFUSED_TOO_CLOSE，拿不到点云则 CLEARANCE_UNKNOWN 拒绝

判据：如果一次"垂直下降"的实测 TCP 在水平方向也移动了，就是走了关节空间，必须停。
```
