## 3. 三次安全事件（全部记录进手册）

### 3.1 `--force` 重挂导致机械臂抽搐着跳回旧位置（最严重）

```text
经过：所有者手动拖动机械臂后，我按自己刚写进手册的"规矩"执行
      python3 scripts/ensure_robot_ready.py --force
      机械臂抽搐着快速跳回上一次轨迹的终点（TCP y 方向 240 mm）
真因：arm_controller 把最后一条轨迹的终点当作保持目标；人手拖动不改变它；
      resend_external_script 会让控制器把这个旧目标重新下发。
      偏差小 → 执行（抽搐）；偏差大 → 机器人以速度超限拒收（示教器 4 万多条 violation）
修复：① execute_assembly_chunks 每次成功后写 runtime/last_commanded_pose.json
      ② ensure_robot_ready --force 比对"实测 vs 最后指令位姿"，偏差 >2° 直接拒绝（退出码 5）
      ③ 手册第 33 条改写为正确做法：不要重挂，直接下发从实测位姿出发的轨迹
```

## 3.4 /dev/shm 自愈清理（脚本 `scripts/clean_dds_shm.py`）

```text
问题：FastDDS 给每个参与者建 /dev/shm/fastrtps_<hash> 段，进程异常退出会残留。
      残留段占住端口 → 新进程建参与者失败（open_port_internal failed）→
      表现为"进程活着、ROS 图里却没有发布者"（今天 move_group 与相机各一次）。
做法：自动识别"没有任何活进程占用"的段并删除，在用的一律不动。
      已接入 start_real_stack.sh：每次起栈前 --clean --threshold 8。

**第一版是个错误**（必须记下来）：
  第一版只扫 /proc/<pid>/maps，把 `_el`（事件循环）文件误判为僵尸删掉——`_el` 是用
  open() 打开的普通文件、**不出现在 maps 里**。结果删掉了在用参与者的事件循环文件，
  运行中的驱动栈通信直接断掉（joint_states 收不到、规划服务消失）。
  修复：占用检测同时扫 maps 与 fd，并且 `_el` 的死活跟随它的主段。
  恢复：停栈 → 清理 → 起栈，臂位未变（0.000），控制链全 True。
  验证：运行中执行清理应报"在用 N，僵尸 0"；测试 test_clean_dds_shm.py 锁住这两条规则。
```

## 3.5 全速冲刺与越界（19:46，所有者按下急停）

```text
现象：机械臂全速偏转，J6 到 157°（越过 ±150°），我们发的轨迹只要 ≤11.6°。
真因（两层）：
  ① 执行器在 NO_MOTION 时自动重发 external_control → 控制器回放记忆目标（已删除该副作用）；
  ② 一旦"下发目标 ≠ 实际位置"，控制权就交给机器人自己的伺服，速度由示教器滑块决定。

  · recover_control*.sh 默认滑块改为 0.3（CS625_SPEED_SLIDER 可覆盖）；
  · 执行中看门狗：任一关节越界立即取消目标；
  · scripts/sync_command_position.py：下发前把控制器记忆对齐实际，实测位移 0.00°。
判据：速度明显快于 3°/s ⇒ 一定是伺服在追，立即拍急停。
```

## 4. 轨道法：从最近成功站位推导相机位（今天验证有效）

```text
问题：工件绕"角点"旋转，位置会变；相机必须跟着转，否则覆盖率下降。
做法（今天验证）：用**同一时刻**的工件位姿与相机位姿算相对向量，再按角度差旋转：
    rel     = T_base_tcp_base − T_base_obj_base      ← 必须同一时刻
    new_tcp = T_base_obj_now + Rz(Δyaw) · rel
    new_q   = Rz(Δyaw) · base_q
验证：+13 → 0（−11.4°）覆盖率 0.987；0 → −9（−8.9°）一次通过 0.968。
注意：必须用同一时刻的工件位姿算 rel，混用会导致覆盖率掉到 0.88。
```

比固定 0° 参考可达率更高、误差不累积。
